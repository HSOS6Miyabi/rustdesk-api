# RustDesk API 性能与数据保存说明

## 日常运行

默认使用 SQLite 时，程序启用 WAL 日志模式，并将数据库连接数限制在四个以内，以减少并发写入造成的竞争。MySQL 和 PostgreSQL 继续使用各自配置的连接池参数。

设备心跳会记录最近在线时间。在线状态采用 15 秒内合并心跳的方式减少数据库写入；正常在线状态更新通常只执行一次数据库更新。首次上线和离线后重新上线时，仍会保存状态变化并产生已订阅的通知。

没有设备策略分配时，程序会跳过高级策略解析。已启用的策略按设备缓存查询结果，管理员修改或删除策略时立即清除当前进程中的缓存。没有活跃会话的设备，第一次空会话心跳会清理数据库中可能遗留的记录，随后五分钟内的重复空会话心跳无需执行会话同步事务。

没有对应消息订阅时，程序会跳过推送通知和管理员邮件的设备、账户信息查询。消息推送和邮件任务在写入数据库后，通过通知唤醒发送协程；任务处于等待重试状态时，按照记录的重试时间处理。安装包任务同样由新任务通知触发，启动时检查尚未完成的任务。

策略分配与通知设置的进程内缓存每 30 秒按需重新检查一次。多 API 实例部署时，在另一实例修改配置后，其他实例最多经过这段时间会重新读取相关信息。单实例部署中的管理操作会立即更新缓存。

## 数据库更新与历史记录

数据库迁移版本为 285。升级时会为五类审计记录的创建时间增加索引，便于按照保存期限删除过期记录。

地址簿同步会批量读取缺少的设备信息，只更新实际发生变化的条目，并批量新增或删除。历史审计记录每次最多删除 500 条，缩短单次数据库写入持续时间。

独立 API 令牌的最近使用时间最多每 60 秒更新一次，避免每次鉴权都执行写入操作。

## 程序停止与数据恢复

正常停止 API 后，程序最多等待八秒，使已接受的内存通知事件完成处理，并将待发送消息写入数据库。发送任务、设备在线状态及其他已提交的数据可以在重新启动后继续读取。超过等待时间或程序被强制结束时，尚未写入数据库的事件可能无法保存。

API 随后关闭数据库连接，使 SQLite 正常处理 WAL 日志文件。备份 SQLite 数据时应先停止 API，并确认已没有其他进程使用数据库。有关三种数据库的备份及恢复步骤，请参阅 [数据库备份与恢复](DATABASE_BACKUP_RESTORE.md)。

## 检查方法

运行完整 Go 测试：

```bash
go test ./... -count=1
```

检查缓存与事件处理的并发访问：

```bash
go test -race ./service ./lib/cache -count=1
```

性能相关测试会统计未使用高级功能时的数据库查询次数，检查设备策略改变后的缓存更新，以及地址簿同步时的重复写入情况。GitHub Actions 还会检查 SQLite、MySQL、PostgreSQL 的数据库兼容性和浏览器功能。
