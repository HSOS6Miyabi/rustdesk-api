# RustDesk API 性能与数据保存说明

## Redis 与本地缓存

未设置 Redis 地址时，API 使用最多 32 MiB 的内存缓存。缓存条目按有效时间自动过期，内存达到上限时移除较久未使用的条目。无需部署 Redis 即可使用普通登录、OAuth 授权和设备管理功能。

设置 `RUSTDESK_API_REDIS_ADDR` 后，默认缓存使用 Redis。也可以将 `RUSTDESK_API_CACHE_TYPE` 设置为 `redis`，并通过 `RUSTDESK_API_CACHE_REDIS_ADDR` 指定缓存 Redis 地址。明确选择 `memory` 或 `file` 时，缓存分别保存在当前进程内存或本地磁盘中。

Redis 可用时，OAuth 登录及绑定过程中的短期授权状态在各 API 实例间共享，五分钟后过期。登录失败次数、IP 封禁记录和一次性验证码也通过 Redis 共享。验证码验证成功后立即删除；失败计数和封禁记录按设置的有效时间过期。Redis 未配置时，以上状态由当前实例的内存缓存和登录限制器管理。Redis 运行中断时，登录限制器会继续执行本机记录的安全检查；共享授权状态需要等待 Redis 恢复。

设备心跳、策略解析结果及推送订阅状态仍在本机进行短期缓存，以减少频繁访问 Redis 和数据库的开销。多实例部署可以启用 `RUSTDESK_API_MULTI_INSTANCE_CACHE=1`，将这些缓存的更新间隔从约 30 秒缩短为约 5 秒。多个实例之间的 SSE 通知通过 Redis 转发。修改设备策略及通知设置后，程序还会通过 Redis 通知其他实例立即清除相关缓存；Redis 暂时不可用时，仍按缓存有效时间重新读取数据库。



## 日常运行

默认使用 SQLite 时，程序启用 WAL 日志模式，并将数据库连接数限制在四个以内，以减少并发写入造成的竞争。MySQL 和 PostgreSQL 继续使用各自配置的连接池参数。

设备心跳会记录最近在线时间。未订阅设备上线和离线通知时，管理界面直接使用设备最近心跳时间判断在线状态，不再维护第二份在线记录。需要上线或离线通知时，程序每 15 秒最多处理一次同一设备、同一 IP 的在线状态更新，并保存状态变化及相应通知。

没有设备策略分配时，程序会跳过高级策略解析。已启用的策略按设备缓存查询结果，管理员修改或删除策略时立即清除当前进程中的缓存。过期会话由后台任务按最早到期时间清理；当所有设备均没有有效会话和待处理断开请求时，程序每 30 秒按需检查会话表，空会话心跳无需执行会话同步事务。存在活动会话时，短时间内相同的连接集合会减少重复写入。远程会话及断开请求仍会正常保存并处理。

没有对应消息订阅时，程序会跳过推送通知和管理员邮件的设备、账户信息查询。消息推送和邮件任务在写入数据库后，通过通知唤醒发送协程；任务处于等待重试状态时，按照记录的重试时间处理。安装包任务同样由新任务通知触发，启动时检查尚未完成的任务。

策略分配与通知设置的进程内缓存每 30 秒按需重新检查一次。设备管理命令更新策略分配成功后，同一实例立即清除相关缓存。缓存刷新查询在公共状态互斥锁之外执行，数据库响应缓慢时不会长期占用该锁。多 API 实例部署时，其他实例仍可能在缓存有效期内暂时使用旧配置，安全策略变更需要按部署方式考虑这一延迟。

## 数据库更新与历史记录

数据库迁移版本为 288。升级时新增两张事件暂存表，用于保存已经接受、尚待生成发送记录的推送事件与管理员邮件事件。原有审计清理索引继续保留。

地址簿同步会批量读取缺少的设备信息，只更新实际发生变化的条目，并批量新增或删除。历史审计记录每次最多删除 500 条，缩短单次数据库写入持续时间。

独立 API 令牌的最近使用时间最多每 60 秒更新一次，避免每次鉴权都执行写入操作。

## 程序停止与数据恢复

启用相应通知后，程序先将重要事件保存到数据库，再由后台任务生成发送记录。即使进程意外停止，重启后也会重新处理数据库中的事件。已经写入发送记录的通知会继续按照原有重试规则发送。高频设备在线状态仍使用短时间内的合并处理方式。正常停止时，程序先停止接受新的内存事件，等待已接受的设备状态事件处理完毕，再通知后台任务结束，最长等待 30 秒；确认后台任务已退出后才关闭数据库连接。若数据库不可用，系统会记录无法保存的事件数量和错误信息。

API 随后关闭数据库连接，使 SQLite 正常处理 WAL 日志文件。备份 SQLite 数据时应先停止 API，并确认已没有其他进程使用数据库。有关三种数据库的备份及恢复步骤，请参阅 [数据库备份与恢复](DATABASE_BACKUP_RESTORE.md)。

## 检查方法

运行完整 Go 测试：

```bash
go test ./... -count=1
```

检查缓存与事件处理的并发访问：

```bash
go test -race ./service ./lib/cache -count=1
```

性能相关测试会统计未使用高级功能时的数据库查询次数，检查设备策略改变后的缓存更新，以及地址簿同步时的重复写入情况。GitHub Actions 还会检查 SQLite、MySQL、PostgreSQL 的数据库兼容性和浏览器功能。

## 进一步减少的常规开销

默认关闭 IP 封禁时，HTTP 请求无需读取登录失败次数；登录验证码继续独立工作。设备重复上传相同系统信息时，不再更新设备信息表。常规访问令牌通过一条关联查询读取账户状态与令牌，保留数据库中的即时撤销检查。推送事件批量读取收件渠道，共享地址簿一次读取所需共享规则后统一计算权限。


## 通知历史记录的保存期限

个人推送与管理员邮件的成功发送记录默认保存 30 天，失败记录默认保存 90 天，均可在“日志保留设置”中调整；设置为 0 可保留全部历史记录。清理时每批最多删除 500 条，保留未完成的发送任务和事件暂存记录。

## 高级功能的按需操作

设备没有订阅上线、离线通知时，管理控制台根据设备最近心跳时间显示在线状态，省去额外的在线状态数据库写入。需要上线或离线通知时，仍按原有时间间隔记录状态变化，并由事件暂存表统一处理通知。系统会缓存少量高级策略分配所涉及的设备、用户与设备组编号；未分配策略的设备不再执行额外策略查询。没有待处理远程断开请求时，活动会话心跳也会跳过相应查询。多实例环境会按短时间间隔重新读取待处理断开请求，以保证其他实例新增的请求可以生效。

管理控制台只读的地理位置及设备在线状态查询不再产生管理操作审计记录。启用文件缓存时，后台每天清理过期缓存文件，并保留缓存目录中的其他文件。

## 多实例事件处理

只有多个 API 实例共享数据库时，才需要配置 `RUSTDESK_API_SHARED_EVENT_WORKERS=1`。共享模式通过数据库条件更新认领待处理事件，异常退出后在 60 秒处理期限结束时重新提供事件处理机会，并每五秒检查一次其他实例写入的消息。默认单实例模式继续使用事件通知唤醒后台任务，避免周期性查询。

## 设置中心与通知任务恢复

系统管理员可以在设置中心查看全部全局设置的当前运行值、来源、网页覆盖和待重启状态。运行中的服务使用启动时装载的配置，普通请求不需要为每项设置重复读取数据库。

通知事件暂存表记录失败次数、下次重试时间和处理状态。无法解析的事件会单独进入失败状态，后续有效事件继续处理；管理员可查看并重新提交失败事件。在多实例共享数据库模式下，只有当前认领者可以更新相应事件处理状态。

正式发行版 `v3.0.0-api.107` 的数据库迁移版本为 **290**。运行与性能检查见 [性能测试说明](PERFORMANCE_TESTING.md)。
