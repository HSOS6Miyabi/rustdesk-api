# 性能与数据保存测试

本文说明如何检查 RustDesk API 的数据库访问、缓存、后台任务和程序停止行为。测试应在独立环境进行，禁止使用真实账户密钥和业务数据库直接进行压力测试。

## 常规检查

```bash
go test ./... -count=1
go test -race ./service ./lib/cache ./http/... -count=1
go build -o /tmp/rustdesk-api ./cmd/apimain.go
node --check resources/admin/app.js
node --test resources/admin/app.test.cjs
```

GitHub Actions 会另外检查 SQLite、MySQL、PostgreSQL 的升级过程、浏览器交互、客户端安装任务和发布构建。对于设置中心的启动覆盖和数据保存，还可执行：

```bash
bash scripts/test_settings_startup.sh /tmp/rustdesk-api
```

该脚本在临时目录创建 SQLite 数据库，检查环境变量与数据库覆盖的优先顺序，并通过 SIGTERM 停止 API。运行结束后自动删除临时数据。

## 重点测试项目

| 场景 | 应记录的指标 | 期望行为 |
| --- | --- | --- |
| 设备没有高级策略 | 单次心跳 SQL 查询次数、写入次数 | 跳过策略明细查询；继续执行必要的设备身份核对 |
| 设备没有上线离线订阅 | 在线状态表写入次数 | 通过设备最近心跳时间判断在线状态 |
| 设备有高级策略 | 命中缓存比例、更新延迟 | 本实例修改策略后及时清除对应缓存 |
| 多个管理员角色 | 角色读取和用户组成员查询次数 | 有效角色合并读取，用户组成员批量查询 |
| 批量推送 | 发送任务条数、不同渠道数、渠道读取次数 | 按不同渠道批量读取，避免每条任务重复读取 |
| 单个损坏的通知事件 | 后续有效事件处理数量 | 失败事件单独保留，其他事件继续执行 |
| 多实例共同处理通知 | 数据库认领次数、重复发送次数 | 同一条记录只有当前处理者可以修改处理状态 |
| 空安装包任务队列 | SQL 元数据查询次数、协程数量 | 不持续读取数据库表结构 |
| 进程正常停止 | HTTP 请求完成时间、事件保存时间、数据库关闭时间 | 已提交的任务可在重新启动后恢复 |
| 重建 Docker 容器 | SQLite、启动配置文件与已保存应用设置 | 持久化数据不受容器重建影响 |

## 比较方法

在相同的代码版本、模拟设备数量、数据库类型和并发数量下分别记录优化前后的运行数据。建议模拟 100、1,000 和 10,000 台设备，包含关闭高级功能、少量订阅、大量订阅三种情形。

记录请求耗时的中位数、第 95 百分位数和第 99 百分位数，单请求 SQL 查询与写入数量，CPU 使用率、内存占用、数据库连接数和协程数量。对于 MySQL、PostgreSQL 的索引调整，需要同时比较查询耗时和新增记录的写入成本。

SQLite 可使用 `EXPLAIN QUERY PLAN` 检查索引；MySQL 可使用 `EXPLAIN ANALYZE`；PostgreSQL 可使用 `EXPLAIN (ANALYZE, BUFFERS)`。对于涉及用户或令牌的 SQL，测试日志应隐去真实凭据。

## 通知事件恢复

事件暂存表记录 `status`、`attempts`、`next_attempt_at`、`last_error` 和共享处理信息。暂时失败会重试；无法解析的内容进入失败状态，管理员可在设置中心查看并重新提交。投递记录有唯一标识，用于减少重新处理时的重复发送。

需要分别验证正常停止、数据库暂时不可用、进程异常终止以及多个实例同时处理。对外部邮件或推送平台，如果请求已经成功但数据库尚未记录发送结果就发生异常，重试仍可能带来重复通知，测试报告应说明这种情况。

## 测试结果记录

每次性能改进应记录 Git 提交、数据库类型和版本、测试机器配置、模拟数据量、并发数量、执行命令、查询次数、请求响应时间及实际结论。首次建立测量结果后，将同一组测试用于后续提交的比较。对请求时间明显增加或数据库写入次数上升的改动，应重新检查原因并修正实现。
Docker 和普通服务器的停止测试应记录从发送 SIGTERM 到进程退出的时间，检查是否存在未完成的请求和后台任务。建议给 Docker 至少 75 秒的停止期限，包括最多 20 秒的 HTTP 请求关闭时间，以及最多 30 秒的后台任务停止时间。
